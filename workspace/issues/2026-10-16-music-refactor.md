## 本轮参考 APK：CRMusic 原型

本次用户上传的 `base.apk` 已实际检查，确认是一个独立的 CRMusic legacy 音乐应用原型，不是 ElysiaFloat 当前仓库中的既有文件。附件信息：

```text
来源：当前会话上传 uploads/base_31-110870164.apk
大小：262 KB
SHA-256：`cde6ef2de613e8cd3d19f624b59f4a06c16fba3a935d93728ccb5a417be7e685`
```

APK 中可确认的结构和可借鉴点：

- 独立搜索页、播放器页、收藏页、下载页、历史页、歌单详情页、设置页和文件/导入页；
- `MusicPlayerService` + Android `MediaPlayer`，支持后台播放和通知控制；
- `CRDownloadManager`，独立下载任务和下载卡片；
- `FavoriteStore`、`PlaylistStore`、播放历史 SQLite 表；
- 歌词接口、本地歌词缓存、封面接口、歌单搜索/详情接口；
- 播放、暂停、上一首、下一首、循环、随机、进度拖动、歌词同步；
- 下载位置、自动下载、图片缓存、主题/深色模式和背景氛围效果等设置项；
- XML 原生布局中使用独立的列表、卡片、播放器控制栏和 Tab 导航，说明其页面职责划分清楚。

不直接复制的部分：

- 不复制其 APK 代码、签名、资源或第三方音源；
- 不把其公共服务或版权内容当成 ElysiaFloat 的固定依赖；
- 只借鉴功能分层、状态模型、缓存和页面适配思路。

## ElysiaFloat 音乐目标

### 功能完整性

- 多目录、多 Provider 搜索，结果合并、去重、来源标识和失败降级；
- 播放、暂停、继续、上一首、下一首、停止、循环、随机、进度拖动；
- 歌词获取、解析、滚动、高亮、点击定位和歌词失败时继续播放；
- 收藏、收藏列表、播放历史和后续歌单/播放队列；
- 单曲缓存下载、下载状态、失败原因、断网播放、单曲删除和全部清理；
- 封面、歌曲元数据、来源/音质信息和后台原生播放。

### UI 和适配

- 保持 ElysiaFloat 粉白渐变、圆角、轻量悬浮窗风格，不照搬 CRMusic 的整套视觉资源；
- 将“搜索/收藏/缓存/历史/歌单/设置”作为清晰的页面或 Tab，不把全部功能堆在搜索结果页；
- 小尺寸悬浮窗、普通竖屏、长屏、横屏和系统 Insets 下都能滚动和点击；
- 歌曲标题、歌手、封面、按钮和下载状态要有明确的压缩/省略规则；
- 播放器控制栏固定，列表区域独立滚动，歌词弹层不能遮住系统返回和关闭动作；
- 低版本 WebView 不依赖不稳定 CSS，必要时使用现有兼容类和降级布局。

### 速度目标

- 搜索请求按来源并行，单个来源超时不阻塞其它来源；
- 首屏先展示可用结果，歌词和封面异步补齐；
- 播放地址短时内存缓存，预取下一首但不长期保存签名 URL；
- 缓存下载走后台线程、临时文件和进度回调，不阻塞 WebView；
- 列表最多分批渲染，避免一次生成过多 DOM；
- Provider 健康状态、超时和错误码可见，减少重复等待失效来源。


## 一、调研结论

本次检索到多个名称包含 CRMusic 的公开项目，名称并不唯一。当前参考了两个具有代表性的设计方向：

1. `LGCR837/crmusic`：单文件、零依赖、响应式音乐播放器，重点是播放器状态、歌词同步、移动端布局、控制栏和缓存友好的前端播放体验；
2. `criveros93/CRMusic`：搜索、异步下载、任务 ID、状态查询、音频文件输出和 REST API 的后端任务模型。

没有直接复制第三方代码，也没有把第三方项目的音频源、版权内容或后端部署当作 ElysiaFloat 的默认依赖。借鉴内容为：

- 播放器 UI 与播放状态分离；
- 搜索、解析播放地址、歌词和下载缓存分层；
- 下载采用异步任务、状态和结果文件；
- 移动端播放器适配和歌词同步；
- 来源失败时切换候选来源，而不是只等待一个接口。

## 二、当前旧实现的问题

旧实现把音乐功能集中在 `10-music.js`：

- GD Studio 和 Meting 混合在同一个脚本；
- 搜索使用 `Promise.any`，只取第一个成功来源；
- 结果没有合并去重；
- URL 解析没有明确的来源、目录和健康状态；
- `mGetUrl()` 会对所有来源盲目重试；
- 失败时回退到网易外链，容易遇到 302、签名过期或无效 HTML/JSON；
- 缓存下载之前没有最终 URL、Content-Type 和音频文件头校验；
- 缓存默认写入 App 私有目录，用户无法直接找到；
- 没有来源健康记录、失败原因和下载任务状态；
- 搜索目录固定为少数来源，曲库覆盖不足。

## 三、本轮已完成的第一轮重构

### 3.1 统一请求和来源健康

新增音乐请求层：

- `musicRequest()` 统一调用 `nativeReq()`；
- 统一检查 HTTP 状态；
- 统一记录来源成功/失败；
- 保存来源健康到 `via_ai_music_source_health`；
- 错误包含来源和 HTTP 状态；
- 音乐目录可配置。

### 3.2 多目录搜索

默认目录：

```text
netease,tencent,kugou,kuwo
```

GD Studio 和 Meting 会按目录尝试：

- 搜索结果并行收集；
- 多来源结果合并；
- 按来源、ID、名称和作者去重；
- 单次最多保留 60 条结果；
- 一个来源失败不会阻止其它来源返回。

设置中增加：

```text
音乐来源目录
```

可以通过逗号修改，例如：

```text
netease,tencent,kugou,kuwo
```

具体目录是否被远程服务实现，仍以服务返回为准；不可用目录会被跳过。

### 3.3 播放地址解析

现在优先使用歌曲所属的：

- provider；
- catalog；
- Meting endpoint；

失败后再尝试其它来源，不再直接使用固定网易外链作为无条件成功回退。

### 3.4 缓存下载修复

原生缓存下载现在：

1. 手动跟随最多 6 次 HTTP/HTTPS 重定向；
2. 检查重定向目标协议；
3. 检查最终 HTTP 状态；
4. 检查 Content-Type；
5. 检查 MP3、Ogg、FLAC、ID3 或 MPEG 音频文件头；
6. 先写入 `.part` 临时文件；
7. 下载完成并通过校验后再改名；
8. 错误时删除临时文件；
9. 单曲最大 150MB。

这解决了“缓存失败显示 302”时只报状态、不解析最终资源的问题。

### 3.5 缓存目录可见性

有公共存储管理权限时，缓存目录改为：

```text
Music/ElysiaFloat/cache
```

没有公共存储权限时，回退到 App 私有目录。

音乐界面增加：

- 缓存歌曲数量；
- 缓存总大小；
- 当前缓存路径；
- 清理全部缓存。

```json
{
  "ok": false,

  "retryable": true,
  "requestId": "..."

```

### 4.4 下载任务模型

参考异步下载 API 的任务状态模型，但在本地实现：

```text
QUEUED
→ RESOLVING
→ DOWNLOADING
→ VALIDATING
→ READY
→ FAILED
→ CANCELLED
```

每个下载任务记录：

- 任务 ID；
- 歌曲名称和作者；
- 来源；
- 最终缓存路径；
- 下载字节数；
- 总字节数；
- 进度；
- 错误码；
- 创建时间；
- 完成时间。

## 五、版权和稳定性边界

- 不把某个公共 API 宣传成永久稳定服务；
- 不内置第三方 API Key；
- 不保存短期签名 URL 作为永久资源；
- 缓存只处理用户有权访问的公开音频资源；
- 不通过 Root、Shizuku 或 Termux 绕过版权、登录或访问控制；
- 来源服务异常时显示真实失败原因；
- 用户自定义来源必须经过 HTTPS、超时和响应校验。
