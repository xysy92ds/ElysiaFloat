# 市场定位评估与工程修补方案

更新时间：2026-10-07
评估对象：ElysiaFloat（`com.elly.assistant`，0.6.2，本地持续开发，未提交）
评估方法：仓库代码实测 + 同类项目公开数据抽样 + 类别化对比
状态：评估结论与修补路线，待评审后并入 `current.md` 执行

> 评估口径说明：
> - 文中的仓库数据是我本次实际调用 GitHub API 取得的快照，样本很小，只作量级参考，不代表市场全貌；
> - 未取得公开数据的项目按“类别特征”描述，不虚构任何数字；
> - 本评估不包含真实用户量、收入、留存等商业数据，无法据此判断商业可行性。

## 2. 市场类别与各自强项

### 2.1 商业手机智能助手

- 强项：模型资源、云端算力、UI 打磨、发布与合规团队；
- 弱项：权限透明度低、用户无法控制读取与操作边界、大多不做完整无障碍操作或做得非常保守；
- 对本项目的启示：**可信与可控是可差异化的点**，不是劣势。

### 2.2 开源 Android 自动化（AutoJs6、Tasker、MacroDroid 类）

- 强项：真机自动化稳定、脚本生态成熟、长期维护；
- 弱项：LLM 原生能力弱、没有任务模型、没有权限分级、没有插件市场；
- 对本项目的启示：**设备操作的可靠性**是它们几十年积累的核心，正是本项目目前最薄的地方。

### 2.3 LLM Agent 框架 / Harness（LangGraph、OpenHands、Pi 等）

- 强项：状态机、流式、取消、重试、工具编排、可观测性；
- 弱项：不是 Android 原生，不处理悬浮窗、无障碍、系统权限；
- 对本项目的启示：**调度器设计直接可借鉴**，但不适合整体替换。

### 2.4 可扩展平台型（AstrBot 类）

- 强项：插件协议、事件机制、配置体系、第三方开发门槛低；
- 弱项：面向聊天/消息平台，不含设备控制与文件工作区；
- 对本项目的启示：**插件协议与开发文档**的方向正确，但本项目还要叠加设备与文件权限约束。

### 2.5 Android Agent + 运行时（Aether 类）

- 强项：运行时路由、Termux 长任务、Shizuku/Root 特权进程、虚拟屏；
- 弱项：体量大、依赖 Compose 与自研内核、对轻量设备不友好；
- 对本项目的启示：**协议层面可借鉴，规模层面不宜照搬**。

### 2.6 ElysiaFloat 所处位置

```text
商业助手        设备控制强、可信度低
开源自动化      自动化强、LLM 弱
Agent 框架      架构强、非 Android
平台型          插件强、无设备能力
Aether 类       运行时强、体量大
────────────────────────────────
ElysiaFloat     悬浮窗 + LLM + 无障碍 + 工作区 + 插件市场，覆盖面最广，单项深度最浅
```

结论：**覆盖面是真实的差异化优势，深度不足是当前的普遍状态。**

- **强项集中在"设计判断"**：权限分级、白名单、逐次确认、插件声明式权限、文档纪律；
- **弱项集中在"工程实现"**：模块化、测试、调度器、发布；
- **设备可靠性是最大短板**，而这恰好是同类开源项目最强、也是用户最在意的一项。

## 4. 客观结论

### 4.1 阶段判定

```text
原型后期 / Beta 早期
```

不是玩具，也还不是产品。主要证据：

- 已有真机可用的核心能力（应用解析、白名单启动、工作区读写、文件复制）；
- 已有多层安全设计，不是简单开关；
- 但缺乏可重复验证、缺发布流程、缺模块边界。

### 4.2 相比市场的真实差距

| 差距 | 具体表现 | 市场参照 |
|---|---|---|
| 可靠性 | 多步设备任务成功率与失败恢复未量化 | 开源自动化项目长期积累 |
| 调度 | 非流式、取消是补丁式叠加 | Agent 框架普遍有状态机 |
| 可维护性 | 前端单文件约 7.5k 行且仍在增长 | 成熟项目普遍模块化 |
| 可验证性 | 测试以结构性断言为主，原生侧无单测 | 成熟项目有 CI 与行为测试 |
| 可信发布 | debug 签名、无 CI、无版本策略 | 商业与主流开源均有 |
| 安全纵深 | 缺提示词注入防御与正式威胁模型 | 商业侧有审核，开源侧多数也没有 |
| 生态 | 插件无签名与撤销 | 平台型项目已具备 |

### 4.3 不构成差距的部分

- 功能构想不落后，甚至超前；
- 权限设计思路不落后于开源同类；
- 悬浮窗 + Agent + 工作区 + 插件的组合具有独特性。

**也就是说：差距不在"想做什么"，而在"如何稳定地做到"。**

---

## 5. 差距的结构性成因

1. **功能增速 > 验证增速**：每轮都在加能力，测试和模块化没有同步；
2. **单文件承载全部前端逻辑**：修改成本随行数非线性上升；
3. **安全靠自觉而非机制**：没有"不通过门禁就不能合并"的规则；
4. **范围过大**：Root、Shizuku、Termux、插件市场、外部 Agent 并行推进，每个都停在骨架；
5. **缺少量化指标**：没有任务成功率、取消正确性等可测数据，无法判断改动是变好还是变坏。

## 6. 修补方案

### 主线一：工程解耦（优先级最高）

目标：把 7.5k 行单文件拆成可独立修改、可独立测试的模块。

```text
assets/src/
├── core/        配置、存储、工具函数、错误码
├── ui/          主界面、设置、任务舱、弹窗、样式
├── tasks/       任务模型、状态迁移、任务舱逻辑
├── agent/       调度器、状态机、工具网关、超时与取消
├── plugins/     清单校验、权限、沙箱、市场
├── memory/      记忆库与合并策略
├── media/       音乐、TTS、翻译
└── build.js     按顺序拼接为 assets/index.html
```

要求：

- 运行期产物仍是单个 `index.html`，不改动 WebView 加载方式；
- 每个模块可被 `smoke.js` 独立加载测试；
- 迁移必须分批，每批保持构建和冒烟通过。

### 主线二：可验证性

1. 行为测试（新增 `tools/behavior.test.js`）：
   - 任务状态迁移合法性（非法迁移必须被拒绝）；
   - 取消后不再产生新动作；
   - 迟到回调不写入状态；
   - 工作区路径越界被拒绝；
   - 快照创建与回滚一致性；
   - 插件权限拒绝路径。
2. Kotlin 单测（`app/src/test/`）：
   - `TaskWorkspace`：路径解析、越界、快照、恢复；
   - `TermuxWorker`：任务校验、工作目录校验；
   - `RootWorker`：操作白名单拒绝。
3. CI（GitHub Actions）：
   - 构建 Debug；
   - 跑冒烟与行为测试；
   - 跑 Kotlin 单测；
   - 失败即阻断。

### 主线三：可信发布

1. 生成 keystore 并启用 release 签名；
2. 版本策略：`versionCode` 单调递增，`versionName` 语义化；
3. 每次发布产出 APK + SHA-256 + 变更说明；
4. 记录真机矩阵结果（Android 版本 × 厂商 × 权限状态）；
5. 隐私与权限声明随包发布。

### 主线四：Agent 可靠性（设备任务）

这是"能否被信任"的核心。

1. 状态机替换补丁式取消：

```text
IDLE → PLAN → ACT → VERIFY → (PLAN | CONFIRM | DONE | FAIL)
```

2. 统一取消：模型请求、截图、Termux 子进程、插件调用共用同一个取消源；
3. 动作后验证强制化：无验证的动作不允许标记成功；
4. 幂等与去重：相同动作 + 页面未变 → 熔断（已有基础）；
5. 成功率量化：记录每个设备任务的步数、重试次数、结果。

### 主线五：安全纵深

1. 明确"内容不等于指令"：屏幕文字、文件内容、网页内容一律视为不可信数据；
2. 危险动作前做意图复核：目标、对象、影响范围，与用户原始目标对照；
3. 正式威胁模型文档：注入、越权、路径穿越、zip bomb、凭据泄露；
4. Root/Shizuku/Termux 分级保持默认关闭，审计不阻塞但必须可查。

### 治理规则（防止再次漂移）

一个功能只有同时满足以下四条，才能从"计划"改为"完成"：

```text
代码实现 + 自动测试 + 真机验证 + 文档同步
```

缺任何一条，只能标记为"基础版"或"未验证"。

## 7. 修补后的路线图

### 优先级重排

原顺序（P0→P4、N1→N10）是"功能优先"。修补后调整为"地基优先、能力后置"。

| 阶段 | 主题 | 内容 | 出口条件 |
|---|---|---|---|
| R0 | 工程解耦 | 拆分前端模块、构建脚本、冒烟适配 | 构建与冒烟全绿，APK 功能不变 |
| R1 | 可验证性 | 行为测试 + Kotlin 单测 + CI | CI 全绿，关键路径有测试 |
| R2 | 调度器重构 | 状态机、统一取消、验证强制、流式评估 | 取消后无残留动作，成功率可统计 |
| R3 | 发布工程 | 签名、版本策略、校验、真机矩阵 | 产出可分发 Release 包 |
| R4 | 安全纵深 | 威胁模型、注入防御、危险动作复核 | 威胁模型逐项有对策 |
| R5 | 能力扩展 | 文件格式、Termux L2、Runtime 路由、插件分级 | 每项具备测试与真机结果 |
| R6 | 高权限 | Shizuku、Root 扩展、自动开启无障碍、Termux L3 | 默认关闭，审计完整 |
| R7 | 生态与外部 Agent | 插件签名与撤销、外部 Agent 适配 | 按需，最后推进 |

### 与原计划的映射

- 原 P0～P4：基础已落地，保留为 R2/R5 的输入；
- 原 N1～N10：整体后移到 R5～R7，N4/N5（文件格式）可在 R5 提前；
- DSH：保持在最后，且必须满足 R0～R3 全绿后才启动；
- UI 类修复：可持续并行，不属于阶段阻塞项。

## 8. 需要跟踪的量化指标

| 指标 | 当前 | 目标 |
|---|---|---|
| 前端单文件行数 | 约 7.5k | 单模块 < 1k，产物不变 |
| 自动化测试用例数 | 结构性为主 | 行为用例 > 30，Kotlin 单测 > 20 |
| 设备任务成功率 | 未统计 | 先统计，再逐步提升 |
| 取消正确性 | 部分（令牌） | 全覆盖，无残留动作 |
| 构建可重复性 | 手动 | CI 自动 |
| 发布签名 | debug | release |
| APK 体积 | 约 2.3 MB | 保持在 10 MB 内 |

## 9. 范围建议

不建议并行推进全部高权限能力。建议：

```text
先做深一条：设备操作可靠性（R2 + 主线四）
```

理由：

- 这是同类开源项目最强、也是用户最能感知的一项；
- 完成后，Root/Shizuku/Termux 才有稳定的调用基础；
- 反过来，先上高权限而没有可靠调度，只会放大误操作风险。
